# write-spec

명세는 AI가 쓰고 사람은 결정만 한다. 코드로 확인할 수 있는 내용은 사람에게 묻지 않는다.

## 1. 파일 준비

- 번호: `docs/specs/`의 기존 `NNNN-*.md` 중 가장 큰 번호 + 1. 파일명은 `NNNN-영문-주제.md`.
- 카드: `docs/specs/CARD_TEMPLATE.md`를 복사한다.
- 전체 명세: `docs/specs/TEMPLATE.md`를 복사한다.
- 같은 기능의 기존 명세가 있으면 새로 만들지 않고 그 명세를 갱신한다. 이미 적용된 결정을 바꿀 때만 새 명세를 만들고 대체 관계를 양쪽에 적는다.
- `docs/specs/README.md` 표에 행을 추가한다 (`종류`: `card` 또는 `full`).

초안 작성은 직접 하거나 `spec-drafter` 에이전트에 맡긴다. 맡길 때는 요청 원문, `start-task`의 판정·조사 결과, 대상 파일을 함께 넘긴다.

## 2. 채우기

- 템플릿 칸은 실제 코드·스키마·테스트를 조사해 채우고 근거 경로를 적는다.
- 해당 없는 칸은 지우지 말고 이유를 한 줄로 적는다.
- 확인할 수 없거나 다른 모듈과 합의가 필요한 항목은 `TBD`로 남긴다. 1번 기능 변경이 필요한 항목은 "구현 보류"로 표시한다.
- 요청·응답 예시는 합성 데이터만 쓴다.

## 3. 결정 질문

`TBD` 중 사람이 정해야 하는 것만 모아 한 번에 묻는다. 질문마다 선택지 2~4개, 각 선택지의 영향, 권장안을 붙인다. 답을 기다리는 동안 그 결정에 의존하지 않는 범위는 계속 구현한다.

## 4. 상태

| 상태          | 언제                                                                                    |
| ------------- | --------------------------------------------------------------------------------------- |
| `draft`       | 이번 구현 범위에 영향을 주는 `TBD`가 남아 있음                                          |
| `ready`       | 이번 구현 범위의 입출력·소유권·전환·수용 기준이 정해짐                                  |
| `implemented` | 구현 후 `verify`로 실제 실행한 검증 결과를 기록함. 실행하지 않은 항목은 "미검증"과 사유 |
| `superseded`  | 후속 명세로 대체됨. 대체 문서 링크                                                      |

과거 보고서의 통과 횟수나 제안 이미지를 이번 검증 결과로 쓰지 않는다.
