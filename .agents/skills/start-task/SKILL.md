# start-task

작업 요청을 받으면 구현 전에 아래 순서로 진행한다. 질문·설명만 요청받았으면 이 스킬을 쓰지 않는다.

## 1. 경계 확인

`npm run check:boundaries`를 실행한다. 실패하면 덮어쓰거나 기준을 갱신하지 말고 바뀐 1번 전용 파일 목록을 개발자에게 보고하고 멈춘다.

## 2. 대상 분류

`docs/current/MODULE_BOUNDARIES.md`의 표로 변경 대상을 분류한다.

| 분류                                             | 처리                                                                                                |
| ------------------------------------------------ | --------------------------------------------------------------------------------------------------- |
| 1번 접수 에이전트 기능·동작 변경                 | 구현하지 않는다. 필요한 변경과 이유만 남기고, 2·3번 쪽 호환 어댑터로 해결할 수 있는지 먼저 검토한다 |
| 1번 전용 파일 (`scripts/module-1-baseline.json`) | 편집·삭제·이동하지 않는다                                                                           |
| 공용 파일                                        | 1번이 쓰는 부분을 유지하는 범위에서 변경. 완료 전에 `boundary-review`                               |
| 2·3번, 기타                                      | 변경 가능                                                                                           |

## 3. 겹치는 기능 조사

바꿀 기능과 같은 역할을 하는 코드·API·DB·화면이 이미 있는지 찾는다. 검색할 곳이 한두 군데면 직접 찾고, 독립된 조사 질문이 여러 개면 `explorer` 에이전트에 나눠 맡긴다. `docs/archive/**`는 기본 입력으로 쓰지 않는다.

## 4. 명세 규모 판정

위에서부터 처음 해당하는 행으로 판정하고, 판정과 근거를 한 줄로 보여준다. 개발자가 다른 규모를 지정하면 그것을 따른다.

| 규모      | 기준                                                                                                     | 다음 단계           |
| --------- | -------------------------------------------------------------------------------------------------------- | ------------------- |
| 전체 명세 | 모듈 간 API·이벤트, 데이터 소유권, DB 스키마·마이그레이션, 공용 파일 중 1번이 쓰는 부분 중 하나라도 바뀜 | `write-spec` (전체) |
| 카드      | 2·3번 내부의 새 기능, 사용자에게 보이는 동작 변경, 기존 기능 대체·통합                                   | `write-spec` (카드) |
| 없음      | 그 외 (버그 수정, 내부 리팩터링, 문서·테스트 보강 등). 관련 명세가 있으면 바뀐 사실만 갱신               | 바로 구현           |

예: `판정: 카드 — 3번 내부 예약 목록 필터 추가, 모듈 간 계약 변경 없음`

## 5. 계획 제시

다음을 짧게 제시하고 바로 다음 단계로 진행한다. 개발자 확인이 꼭 필요한 결정이 있을 때만 멈춘다.

- 수정할 파일과 이유
- 실행할 검증 (`verify` 기준)
- 결정이 필요한 질문 (없으면 생략)

이후 흐름: 명세가 필요하면 `write-spec` → 구현 → `packages/contracts/src`가 바뀌면 `contract-change` → `verify` → 공용 파일이 바뀌었으면 `boundary-review`.

## 서브에이전트 사용

- 이 저장소에 정의된 에이전트만 쓴다: `explorer`·`verifier`(T1), `implementer`·`spec-drafter`(T2), `reviewer`(T3). 단계별 모델은 `docs/current/AI_WORKFLOW.md`에 있다.
- 동시에 최대 3개까지 실행한다. 서브에이전트가 또 서브에이전트를 부르지 않는다.
- 위임할 때 모델·effort를 따로 지정해 단계를 올리지 않는다.
- 파일 몇 개를 읽거나 한 곳을 고치는 작은 작업은 위임하지 않고 직접 한다. 결과가 길어 메인 컨텍스트를 채우는 조사·검증 실행, 서로 독립된 작업을 위임한다.
