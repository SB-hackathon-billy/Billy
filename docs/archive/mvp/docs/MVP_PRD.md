# 성북 공유대여 MVP PRD



성북구 1인가구지원센터를 모바일 PWA로 개편한다. 중심 경험은 한국어로 필요한 물품을 말하고, 공공·주민 물품을 함께 찾고, 여러 소유자가 제안한 조건을 비교해 하나를 선택하는 AI 공유대여다. 이번 산출물은 기획·연동 명세이며 앱 구현은 포함하지 않는다.

문서 간 업무·API 정의는 공통 컨트랙트 (공유본 미포함: `COMMON_CONTRACT.md`)를 따른다. 원문은 기획 제안서 (공유본 미포함: `Seongbuk_Share_Proposal.pdf`)와 작성 지시서 (공유본 미포함: `../prompts/seongbuk-mvp-prd-contract.md`)다. 사용자 후속 답변이 제안서보다 우선한다.

| 범위      | 실제 구현할 동작                                               | 데이터·업무 경계                                           |
| --------- | -------------------------------------------------------------- | ---------------------------------------------------------- |

| 주민 신청 | 후보별 요청 전달, 실제 소유자의 승인·거절·조건 변경, 다자 비교 | 서버에 저장하고 다른 사용자 세션으로 전달                  |
| 조율      | AI 가격 추천, 구조화된 변경 제안, 다시 승인 요청, 최종 선택    | 사람의 동의·서버 검증을 통과해야 상태 변경                 |
| 결제      | 최종 조건·금액·가상 결제수단·안내 화면                         | PG·카드 입력·청구·결제 성공 상태 없음                      |
| 기존 센터 | 소개·사업·프로그램·동아리·공간·소식·내 정보 모바일 화면        | 콘텐츠 탐색과 로컬 양식 미리보기. 실제 접수·예약 업무 없음 |

물품 신규 등록·사진 업로드·주민 간 채팅·연락처 교환·지도 기반 실시간 위치·추천 피드·분쟁 처리·푸시/SMS·A2A·타 기관 연동도 이번 필수 범위에 포함하지 않는다. 주민 물품은 미리 적재한다. 실시간 인앱 갱신과 앱 재진입 조회는 포함한다.

제안서 19쪽의 실제 결제 후 대여 확정은 이번 MVP에 도달하지 않는다. `결제 화면 준비 완료`가 성공 종점이다. 거래 완료·실제 예약 완료·보상 지급이라는 문구나 상태를 만들지 않는다. 원 제안의 포인트·지역화폐(21–23쪽)와 확장(26쪽)은 후속 구상이다.

## 3. 사용자와 검증할 가설

요청자는 필요한 물품·사용 기간·만날 수 있는 장소를 말하고, AI가 정리한 내용을 확인한다. 소유자는 자신의 물품에 도착한 카드로 대응한다. 역할은 계정에 고정되지 않으며 거래별로 정해진다. 센터 담당자는 이번 MVP의 조작 주체가 아니다.

검증할 가설은 음성 요청이 수동 검색의 입력 부담을 줄이는지, 여러 소유자의 응답을 한 화면에서 비교할 수 있는지, 실제 두 개 이상 사용자 세션 사이에서 조율이 끊기지 않는지다. 실사용 대여율·반납률·보상 효과는 측정 대상에서 제외한다.

제작 완료 기준은 다음과 같다. 수치는 실증 결과가 아니라 테스트 목표다.

- 정상 시나리오 10회 중 9회 이상이 진행자 개입 없이 결제 화면에 도달한다.
- 하나의 요청에서 서로 다른 소유자 2명 이상이 응답하고 요청자가 비교·선택할 수 있다.
- 잘못된 사용자 승인, 중복 선택, 오래된 조건 선택, 같은 물품·겹치는 기간의 동시 선택이 0건이다.
- 응답 저장 후 연결된 다른 기기 화면 갱신을 정상 네트워크에서 2초 이내 목표로 한다. AI 발화 지연은 별도 측정한다.
- 앱을 종료·재진입해도 이미 접수된 요청과 제안 버전이 보존된다.

## 4. 핵심 사용자 흐름

### 4.1 진입과 음성 요청

첫 화면에 아이디 입력창과 준비된 아이디 예시를 제공한다. 미등록 아이디는 생성하지 않고 안내한다. 진입 후 홈에서 `무엇이 필요하세요?` 음성 버튼을 누르면 마이크 권한을 요청한다. 듣는 중·답하는 중·연결 끊김을 구분하고 음소거·종료·텍스트 전환을 항상 제공한다.

AI는 물품 종류, 시작·종료 일시, 만남 장소 후보를 채운다. `이번 토요일`, `저녁쯤`은 서울 시간 기준의 정확한 날짜·시간으로 다시 확인한다. 예산은 선택 항목이며 음성에 없는 가격·장소·날짜를 확정값으로 만들지 않는다. 사용자는 요약 카드의 `이 조건으로 찾아보기`를 눌러 검색을 시작한다. 음성은 탐색·설명을 맡고, 요청 전송과 최종 선택은 화면 확인을 요구한다.

### 4.2 공공과 주민 후보 탐색

서버가 공공·주민 물품을 함께 조회한다. 공공/주민, 이용 가능 기간, 지정된 데모 만남 장소, AI 추천 금액 또는 공공 데모 요금, 소유자 응답 필요 여부를 표시한다. 자기 물품은 요청 후보에서 제외한다. 재고·일정·데모 자격이 맞지 않는 항목은 사유와 함께 비활성화한다.

요청자는 최대 3개 후보를 선택하고 `이 후보들에게 요청`에서 대상과 조건을 확인한다. 후보 수 제한은 과도한 요청과 데모 복잡도를 줄이기 위한 설계 기본값이다. 여러 소유자에게 전달된다는 문구를 확인 화면에 표시한다. 하나의 물품만 택하는 것도 가능하다. 자동으로 미선택 소유자에게 연락하지 않는다.

공공 후보는 `센터 데모 신청`으로 접수된다. 서버 어댑터가 가용성·데모 자격과 사전 시나리오를 검사해 승인·거절을 반환한다. `신청 여부 확인`은 요청자에게 실제로 이 후보의 데모 신청을 보낼지 묻는 동작으로 정의한다. 관리자 화면이나 숨겨진 직원 역할을 만들지 않는다.

### 4.3 소유자별 요청과 조율

소유자는 요청함의 `빌려주기`에서 물품, 요청 기간·장소, 추천 대여료와 근거, 응답 기한을 본다.

| 조작      | 뜻                                        | 이후 동작                                      |
| --------- | ----------------------------------------- | ---------------------------------------------- |
| 승인      | 표시된 정확한 버전의 조건으로 빌려줄 의사 | 요청자 비교함에 선택 가능한 제안으로 등장      |
| 거절      | 해당 물품 요청을 진행하지 않음            | 해당 후보만 종료. 다른 소유자 요청은 유지      |
| 조건 변경 | 빌려줄 의사가 있고 다른 조건을 제안       | 기간·장소·추천 가격 선택을 바꿔 AI를 통해 전달 |

소유자가 바꿀 수 있는 항목은 대여 시작·종료 일시, 미리 정의된 만남 장소, 허용 가격 범위 안의 금액이다. 이름·전화번호·주소를 자유 텍스트로 교환하지 않는다. 선택 사유는 `일정 조정`, `장소 조정`, `가격 조정`, `기타 조건` 코드로 전달한다. AI 설명은 이 구조화된 정보에서 생성한다.

요청자는 소유자가 제안한 조건을 유지하거나 수정 제안을 보낼 수 있다. 수정하면 이전 승인은 무효가 되고 소유자가 다시 확인한다. 요청자와 소유자의 변경을 합쳐 후보당 최대 3회로 제한한다. 그 뒤에는 현재 유효한 제안을 선택하거나 후보 요청을 닫는다. 반복 조율에서 AI가 사람 대신 승인하지 않는다.

### 4.4 여러 제안 비교와 최종 선택

비교 화면은 공공·주민 후보별로 동일한 항목을 보여준다. 모바일에서는 수평 스크롤만 강요하지 않고 같은 순서의 세로 카드와 `차이만 보기`를 제공한다.

| 비교 항목 | 표현                                               |
| --------- | -------------------------------------------------- |
| 물품·출처 | 대표 이미지, 공공/주민 표식, 가명 소유자           |
| 기간      | 날짜와 시각, 최초 요청과 달라진 부분               |
| 만남 장소 | 데모 장소 이름, 초기 장소 선호와 일치 여부         |
| 총 대여료 | 원화 정수, AI 추천/소유자 변경/공공 데모 고정 표시 |
| 응답 상태 | 응답 대기·제안 도착·거절·만료·선택 불가            |
| 유효 기한 | 서버 기준 남은 시간                                |

기본 순서는 조건 충족 여부, 총 대여료, 응답 도착 시각이다. AI는 차이를 설명하며 선택을 강요하지 않는다. 대기 중인 소유자도 목록에 남긴다. 요청자는 기다리거나 현재 도착한 제안 하나를 최종 선택할 수 있다.

최종 확인에는 선택한 물품·소유자·조건 버전·총액과 `다른 후보 요청은 종료됩니다`를 표시한다. 서버가 해당 버전과 가용성을 다시 검사하고 한 제안만 선택한다. 다른 제안은 `다른 물품 선택으로 종료`가 되며 관련 소유자에게 인앱 상태 변경을 전달한다. 이후 결제 화면으로 이동한다.

### 4.5 결제 화면과 종료

결제 화면은 조건과 데모 요금, 가상 결제수단 표시, `데모 확인 완료` 버튼으로 구성한다. 카드번호·계좌·휴대폰 결제정보를 입력받지 않는다. `실제 결제와 예약이 이루어지지 않습니다`를 표시한다. 버튼은 요청함으로 이동하며 업무 상태를 결제 성공으로 바꾸지 않는다.

선택 과정에서 같은 물품의 중복 선택을 막기 위해 10분의 데모 점유를 둔다. 이는 실제 예약이 아니다. 점유가 끝나도 결과 요약은 열람할 수 있지만 `데모 선택 유효시간 종료`로 표시한다. 새 거래를 시험하려면 새 요청을 만든다.

## 5. AI 대여료 추천 규칙

이 규칙은 사용자에게 위임받아 선정한 **데모 정책**이다. 실제 공공 요금이나 시장가격을 주장하지 않는다. 모든 물품 대여의 표시 금액은 양수이며 보증금·수수료·보상·지역화폐는 계산하지 않는다.

주민 물품에는 `referenceDailyKrw`를 500원 단위의 양수로 적재한다. 대여 기간은 1시간 이상 7일 이하, 30분 단위로 제한한다. 과금 일수는 `ceil(기간 시간 / 24)`다. 기준 총액 B는 기준 일요금과 과금 일수의 곱이다.

- 서버가 하한 L=`max(500, floor(B×0.8/500)×500)`, 상한 U=`ceil(B×1.2/500)×500`을 계산한다.
- AI는 L·B·U 중 한 값을 추천하고 `기준 대여료`, `복수 장소의 조율 편의`, `등록된 운반 부담` 등 허용 근거로 설명한다. 근거는 데모 물품의 구조화된 등록 조건과 사용자가 지정한 장소 후보에서만 가져온다. 근거가 부족하면 B를 추천한다.
- 누구나 L~U 사이의 500원 단위 금액을 제안할 수 있다. 범위를 벗어나면 저장하지 않고 이유를 안내한다. AI가 가격을 직접 청구하지 않는다.
- 기간이 바뀌면 B·L·U와 추천을 다시 계산한다. 장소만 바뀌면 가격 범위는 유지한다. 새 조건 버전은 당사자가 다시 확인한다.
- 선택 예산을 초과한 제안은 명확히 표시하고 자동 선택하지 않는다. 소득·나이·성별·개인 사정에 따라 가격을 바꾸지 않는다.
- AI 오류·시간 초과 시 B를 사용하며 `기준금액으로 안내`라고 표시한다. 같은 조건 해시에는 기존 추천을 재사용해 금액이 흔들리지 않게 한다.

예: 일요금 2,000원인 프로젝터를 30시간 빌리면 2일로 계산한다. B=4,000원, L=3,000원, U=5,000원이다. AI 추천이 4,000원이어도 소유자는 4,500원을 제안할 수 있으며 요청자는 다른 소유자의 총액과 함께 비교한다.

공공 물품은 별도의 고정 데모 일요금×과금 일수로 표시하고 협상하지 않는다. 사용자의 AI 가격 요청은 주민 물품의 조율에 적용한다. 실제 공공 요금·유료화 가능 여부는 센터 협의 사항으로 남긴다.

| 토큰                  | 값                    | 용도                   |
| --------------------- | --------------------- | ---------------------- |

흰색/주요 네이비 대비는 약 11.37:1, 흰색/진한 그린은 약 5.68:1이다. 중간 색과 텍스처는 본문 배경에 겹치지 않게 한다. 색 의미와 대비 계산은 [브랜드 조사](research/center-and-brand.md)에 기록했다.

자체 에셋은 에이전트의 두 잉크 방울 모티프, 공유대여 홈 수채화 그림 1종, 물품 분류 그림 4종 이상, 빈 상태·승인 대기·비교 가능 상태 삽화로 구성한다. SVG·직접 일러스트·Imagegen 생성 등 제작 수단은 열어 둔다. 본 문서 단계에서는 에셋 제작을 수행하지 않는다. 실제 구현 시 생성 이미지와 실물 사진을 구분하고 제작 방식·권리·대체텍스트·용량을 기록한다.

에이전트의 움직임은 실제 상태를 설명한다. `듣는 중`에는 마이크 상태, `찾는 중`에는 서버 조회, `응답 대기`에는 정적인 기다림 표현, `새 조건 도착`에는 해당 소유자 카드 강조를 사용한다. AI가 일을 하지 않는 동안 무한 작업 애니메이션으로 진행을 과장하지 않는다.

## 9. 로컬 배포와 PWA 복구

로컬 PC에서 정적 web·api·worker·PostgreSQL을 실행하고 프록시로 `http://localhost:8000`의 하나의 origin을 제공한다. DB는 외부에 직접 노출하지 않는다. PC 절전·종료 중에는 작업이 진행되지 않고 재시작 후 저장된 작업을 재개한다.

로컬 배포는 앱 서버 위치를 뜻한다. PC의 OpenAI API 호출과 음성 클라이언트의 WebRTC 연결 모두 인터넷이 필요하다. 클라우드 배포·외부 공개 터널·완전 오프라인 AI는 이번 기본 구성에 넣지 않는다. API 키 설정 및 실제 기기 검증 절차는 [기술 조사](research/pwa-and-stack.md)와 공통 컨트랙트를 따른다.

Android Chrome·Samsung Internet의 브라우저와 설치 PWA, iOS Safari와 홈 화면 PWA를 검증 대상에 둔다. 브라우저·OS 최소 버전 숫자는 실제 데모 기기에서 확인 후 고정한다. 문서 조사만으로 모든 갤럭시·아이폰에서 동작한다고 보장하지 않는다.

사용자 동작 뒤의 마이크 권한이 필요하다. 설치는 음성 사용의 필수 조건으로 두지 않는다. 앱 종료·백그라운드·화면 잠금 시 음성 연결이 유지된다고 약속하지 않는다. 브라우저가 중지되어도 이미 접수된 서버 조회·전달·응답 대기·만료는 계속 처리한다. 복귀하면 서버 스냅샷과 이벤트를 다시 읽고, 음성 재시작은 사용자가 선택한다. [MDN 마이크 API](https://developer.mozilla.org/en-US/docs/Web/API/MediaDevices/getUserMedia), [PWA 조사](research/pwa-and-stack.md)

서비스 워커는 정적 앱 shell과 공개 예시 콘텐츠만 캐시한다. 세션·요청·제안·AI 응답은 캐시하거나 오프라인으로 전송 예약하지 않는다. 오프라인에서는 안내와 비활성 상태를 제공한다. 앱 업데이트는 조율 중 강제 새로고침하지 않고 안정된 화면에서 안내한다. 잠금 화면 알림·웹푸시는 이번 완료 조건에 포함하지 않는다.

| 빠른 분류  | `gpt-6-luna`, Decisions API                                            | 의도·다음 처리 경로의 제한된 분류                           |

사용자 표현인 “GPT 라이브”와 “테라”에 대응하는 공식 API 식별자를 확인했다. “디시전 모델”은 별도의 모델 이름으로 단정하지 않으며, 공식 Decisions API에서 사용하는 모델을 `gpt-6-luna`로 선정한다. [GPT-Live](https://developers.openai.com/api/docs/models/gpt-live-1), [Terra](https://developers.openai.com/api/docs/models/gpt-6.1-terra), [모델·API 조사](research/openai-models.md)

모델명은 서버 환경 설정으로 분리한다. 공개 문서상 제공과 이 프로젝트 계정의 이용 권한은 다르며, 계정별 실제 호출·쿼터·한국어 음성 품질은 구현 시작 시 검증한다. 접근 불가 시 조용히 다른 모델로 바꾸지 않고 선택 문서를 갱신한다. 업무 규칙·권한·예약 중복·금액 계산은 모델이 아니라 서버가 결정한다.

스택은 [비교 근거](research/pwa-and-stack.md)를 따른다. 패키지 정확한 버전·lockfile은 구현 착수 시 호환성 확인 후 고정한다. 기능 구현용 저장소 구조는 `apps/web`, `apps/api`, `apps/worker`, `packages/contracts`, `packages/demo-data`를 권고한다.

## 11. 데모 데이터와 시연

| 데이터    | 최소 구성                                                                                                |
| --------- | -------------------------------------------------------------------------------------------------------- |
| 아이디    | `demo-hana`, `demo-duri`, `demo-seul`, `demo-jun`. 모두 합성 인물, 거래별 역할                           |
| 물품      | 공공 4개·주민 6개. 동일 분류의 주민 물품을 서로 다른 소유자 2명 이상에게 배정                            |
| 비교 핵심 | 하나가 프로젝터 요청 → 두리·슬의 프로젝터 제안과 공공 프로젝터를 함께 비교                               |
| 장소      | `place-center`, `place-station`, `place-library`의 가상 시연 장소. 센터 장소 사용 승인으로 표현하지 않음 |
| 가격      | 주민 기준 일요금·공공 고정 데모 일요금, 모두 양수                                                        |
| 예외      | 가용 재고 없음·사용 불가 물품·자격 미충족·거절·기한 만료·동시 선택                                       |

시드는 서버 시작일의 서울 날짜를 기준으로 미래 일정을 만든다. 고정된 과거 날짜 때문에 시연이 실패하지 않게 한다. 시나리오 초기화는 개발용 CLI/seed로만 하며 관리자 UI·공개 reset API를 만들지 않는다. 주민 응답의 정상 경로는 실제 다른 브라우저·기기 사용자가 누른다. 서버가 소유자 응답을 몰래 자동 생성하지 않는다.

시연 순서는 공공 단독 신청, 주민 두 명의 승인/조건 변경과 비교, 한 후보 거절 후 다른 후보 선택, 앱 닫기·소유자 응답·재진입, 두 요청자의 동시 선택 충돌이다. 각 시나리오의 정확한 픽스처와 검증 항목은 공통 컨트랙트에 둔다.

## 12. 병렬 제작과 완료 조건

프론트엔드는 공통 fixture와 mock API로 화면·음성·비교 UI를 만든다. 서버는 같은 스키마로 세션·조회·후보별 상태·원자적 선택·SSE를 구현한다. AI는 고정 입력·출력 fixture로 정보 추출·가격 추천·비교 설명을 구현한다. 셋은 별도 통합 약속 없이도 컨트랙트의 버전·오류·상태·시간·금액 규칙을 공유해야 한다.

| 관문      | 완료 조건                                                                                                     |
| --------- | ------------------------------------------------------------------------------------------------------------- |
| 계약 고정 | 엔터티·상태·명령·이벤트·오류·fixture 합의, 모델 계정 접근 확인                                                |
| 단일 연결 | 두 기기의 서로 다른 아이디로 실제 소유자 승인 전달                                                            |
| 다자 연결 | 2명 이상 제안 비교, 변경 재승인, 하나 선택·나머지 종료                                                        |
| 회복성    | 재연결·중복 클릭·경쟁 선택·만료·worker 재시도 검증                                                            |
| 화면 완성 | C01–C06·M01·대여 화면과 결제 미리보기. 목록/빈 상태·검색·달력/필터·동아리 각 양식 포함, 자체 에셋·접근성 적용 |
| 기기 확인 | Android Chrome/Samsung Internet·iOS Safari/설치 PWA의 실제 기록                                               |

공통 컨트랙트의 수용 시나리오를 모두 통과해야 한다. 최소한의 진단 로그는 사용하되 관리자·운영 대시보드를 추가하지 않는다. raw 음성은 앱 서버에 저장하지 않는다. 위임 처리를 위한 자막은 음성 세션 동안 임시 문맥으로 사용한 뒤 폐기하고 구조화된 요구·제안·행동 기록만 남긴다. API 공급자의 보관 설정은 구현 시 계정 정책과 함께 확인한다.

## 13. 남은 검토 사항

| 항목                    | 현재 기본값 또는 경계                               | 확인할 시점            |
| ----------------------- | --------------------------------------------------- | ---------------------- |
| 사용자 최종 디자인 검토 | 자체 네이비·그린 팔레트와 에이전트 모티프           | 시각 시안 제작 시      |
| 데모 운영 조정          | 후보 3개·수정 3회·응답 24시간·제안 30분·점유 10분   | 시연 리허설 시         |
| 실기기·계정 조건        | 모델 API 권한, 연결 지연, 브라우저 버전·한국어 품질 | 구현 착수·통합 시      |

미정인 실제 기관 연동이나 후속 기능을 이번 MVP의 필수 구현으로 올리지 않는다. 본 버전의 검토는 범위·인터페이스·데모 정책을 대상으로 한다.

## 음성 QA 개정, 계약 0.2.0

음성 통화는 상담원과 채팅하듯 대화하며 물품·사용 기간·만남 장소·선택 예산을 신청서 템플릿에 실시간으로 채우는 단계다. 통화 중 실제 물품 조회나 예약 초안 저장을 하지 않는다. 사용자가 `통화 종료·조회`를 누르면 서버가 마지막 발화를 반영해 초안을 저장하고 정보가 완전할 때 조회한다. 부족한 정보는 요청함에서 보완한다. 조회 결과는 앱 안 알림과 요청함에 표시한다. 푸시·SMS 및 실제 예약·결제는 범위에 포함하지 않는다. Decisions 발화 종료 검사와 지원 범위 가드레일을 적용하며, 실제 사람·휴대폰 통화 품질은 별도 검증한다. 상세 명령·동시성 규칙은 공통 계약 §16이 우선한다.
